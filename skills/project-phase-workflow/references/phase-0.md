# 阶段 0：需求协商

目标是形成用户确认的第一版目标。按全局协作偏好逐步探索；本阶段产出需求，正式产品实现留待方案确认后。

1. 从现有信息了解使用者、真实场景、当前处理方法、困难、输入和期望输出。样本有助于判断时查看真实或脱敏样本。已知内容直接采用，可查技术事实自行核实。
2. 围绕核心任务讨论第一版必须包含、可以延后、暂不实现的内容，以及设备、联网、预算、数据保存和维护限制。按全局规则完成新需求初评；关键未知标待验证，信息足够时收敛，初评不等于真实验证。高成本任务初步估计工作量、草稿轮数和检查点，用于确定第一版规模并收束实现方法；标明估计依据与不确定性，不考虑 OpenCode 侧预算。
3. 为重要需求与验收点建立稳定编号 REQ-01 / AC-01。验收点写清前置条件与输入、操作或触发、可观察结果、通过标准；指标未知时标待定，真实验证、模拟范围及需要用户体验确认的项目分别注明。
4. 明确普通自主决定范围、重要取舍和暂停条件；关键未知交给阶段 0.5 验证。第一版应能完成核心流程，技术占位与演示状态如实标识。

复用或建立 docs/requirements.md、docs/acceptance.md、docs/handoff.md。阶段结束时呈现具体目标、范围、限制、初步完成标准、整体阶段设想与下一步，取得对应确认；已经明确确认的直接记录。

收尾由 GPT 按 [文档完整性](handoff-quality.md) 核对需求基线，记录已检查内容、关键缺口及处理安排；本阶段形成需求，详细技术设计在阶段 0.5 完成。前端始终由 GPT 负责，本次后续实现模型的选择仅适用于可委派的实现范围。

## 收尾时选择实现模型

具体目标确认后、阶段 0 结束前，须让用户选择本次后续实现模型；每次阶段 0 都执行，不能因存在历史选择而略过。本次收尾前用户已明确选定且仍有效时，直接记录，不重复询问。需求协商与技术审阅沿用当前聊天模型。

先用 Python 执行 [last_opencode_model.py](../scripts/last_opencode_model.py)，只读 OpenCode 本地调用元数据。FOUND 时，以返回的完整模型名作为推荐项，并注明记录时间；这是“上一次实际调用”，不以配置默认值、最近选中列表或猜测代替。条件允许时核对当前模型目录的可用性；历史可用不等于当前仍可用。

候选包含该推荐项与 `deepseek/deepseek-flash`，相同项合并，并允许用户手动输入 `provider/model`，需要时附 `#variant`。返回 MANUAL_REQUIRED、文件不可读或工具不可用时，说明无法可靠读取，请用户手动输入完整模型名，不静默指定默认值。不要读取凭据或聊天正文来推断模型。

把用户选择、完整模型名及变体、确认依据记录在 handoff。推荐项不自动提交；等待用户选择期间可整理不依赖该决定的资料，不派发依赖此选择的实现任务。选择与既有执行端不兼容时说明具体影响并取得对应决定，不自动改执行端或聊天模型。

出口：目标及本次后续实现模型已由用户确认，需求基线完整性已核对，初步验收可用，决定可行性的未知已有处理安排。旧项目只讨论本次变化及其影响，保留仍有效的决定。
