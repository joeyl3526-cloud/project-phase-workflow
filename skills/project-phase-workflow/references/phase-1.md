# 阶段 1：核心版本实现与审阅

目标是完成第一版核心完整流程。先定位本轮角色：实现者或审阅者。

## 实现

沿用技能入口的职责边界：GPT 实现并修改前端，OpenCode 仅实现获准的非前端范围。混合任务先明确归属与接口，前端或共享契约的变更交 GPT 处理。

读取交接、批准需求、设计与相关 AC；核对代码、已有修改、必要环境和基线，按技能入口核对运行选择。明确本轮范围、检查点和交回对象，普通实现细节自行处理。高成本任务按约定的草稿轮数、检查点等迭代边界执行；达到边界时交回已有成果、问题和建议。

按依赖完成可检查的小步，尽早贯通核心流程。复用已有结构，必要时调整；记录重要理由。可用新方法解决当前问题，新增产品能力按已批准范围处理。保护用户数据和已有工作，按有意义的变化保存本地版本。

实现高风险功能前，按已确认需求准备少量有区分力的关键组合场景或反例，并优先拆成可验证的小批次；没有对应风险的简单改动不增加固定流程。检查点和 A/B 授权不因此改变。

按 [测试策略](testing.md) 以有意义的改动批次检查本轮行为与受影响回归，沿用有效基线，不为每次小改或修复默认重跑全量。保存功能检查重启读取，界面功能检查实际操作，外部能力分别说明模拟与真实结果；检查力度匹配影响。

出错时先自行取得可访问的代码、日志和环境证据；仍缺关键内容时，只请用户补充无法自行取得的信息，并说明收集方法。随后复现、检验原因，作足以解决根因的修改并复验。反复失败且无新证据时重新诊断；重构或重写依据结构适配、兼容和成本决定。测试标准依据需求，发现测试自身错误可修正并说明依据。

到检查点时交回成果版本、变化、对应 REQ/AC、自检结果、失败/跳过/未测、证据和已知问题。行为相关未提交修改以差异或补丁明确标识。对话交回按技能入口附验收清单；执行中新增需求或关键计划调整按全局规则处理。更新运行说明及交接。

## 审阅

GPT 按 [OpenCode 成果审阅](strict-review.md) 核对原要求、实际差异、职责边界和证据，判断有实质价值的替代路径。阶段检查限于本轮验收及受影响行为。已有有效证据直接引用，需独立实跑或补证据时按测试策略选择检查。

审阅期间保持成果对象稳定。默认记录问题并交回实现者；需要直接修复时，先记录原问题，按授权切换实施步骤，再对新版本复验。

每条问题写清对应要求、版本、证据或复现、影响和通过条件。区分必须修复的缺陷、必须补充的验证、一般问题和可选建议；证据不足标待验证。实现者可以提出反证，争议按要求和证据解决。

核心要求失败或必要证据缺失时，结论为不通过或无法完成验收。所有强制项在约定环境通过、无阻断缺陷，才给出对应范围的通过结论；新的带限制交付取舍交用户决定。代码已写、构建成功、测试数量与工作区干净各有证明范围。

## 修正与接续

按技能入口中的 A/B 处理审阅结果：A 继续批准范围内的修复、补验证和复验；B 呈现结论与推荐后等待。重复失败先改进诊断，达到批准目标后结束。

记录本阶段状态为实现自检完成、自审完成、单独审阅通过或仍待真实/用户验收，说明当前可用范围及缺口。使用 OpenCode 时，实际任务和成果必须可定位；缺少互联时给出可执行的文件交接。

出口：核心完整流程满足强制验收，所需证据齐备，交接与使用说明准确。后续任务依据项目已批准计划和推进模式安排。
