# 按影响选择测试与复用证据

阶段 0.5 安排验证、阶段 1～n 实现/修复/审阅及最终验收时使用本规则。按本轮验收条件、实际改动及受影响行为选择能判断结果的检查，以有意义的改动批次为单位。用户明确要求和项目放行规定的强制检查照常执行。

## 何时收尾

本轮必验项已经由当前检查或仍有效的证据覆盖，且无影响本轮交付的未解决问题时，停止执行测试并交回结果。保存、小步提交、验收表、角色切换或报告修改均不刷新已有证据。强制项失败或必要证据暂时无法取得时，如实记录失败或阻塞，按实际原因修复或交回。无新证据时不重复同一失败命令。

追加反例、复跑或扩大范围前，能指出它要验证的受支持场景、实际改动或具体现象，以及结果可能改变的交付判断。猜想中的输入、单纯增加测试数量或再确认一次，均不足以触发测试。重现有明确迹象的偶发故障时可按诊断需要重复运行。

## 实现与修复

先核对已有基线是否仍有效。有可复查的同版本失败证据可直接用于定位。基线不明、存在并发改动或环境漂移时，按实际变化补足所需检查。

普通批次检查新增或修复行为、相关正常与错误路径及受影响调用方。文案和注释检查内容，局部界面改动优先在实际页面检查受影响的用户操作和反馈。只修测试或辅助函数时，检查它能否识别成功和失败，并验证受影响用例。共享状态、持久化、权限、并发和外部副作用按实际影响考虑跨模块检查。

修复先验证原失败和受影响回归。同一批次可合并多个相关修改，按需要运行一次能提供所需证据的检查。相关套件已覆盖的用例直接引用结果。测试本身有误时可按原验收标准修正，不以删减有效覆盖制造通过。

## 扩大范围与检查点

局部检查覆盖不了具体风险时，先扩大到受影响模块或核心流程。共享依赖、构建配置、跨模块契约变化或局部失败暴露更广影响时，按实际依赖判断范围。全量只在项目约定的检查点要求、改动影响广或难以可靠界定且较小范围不足以验证，或已知全套比可靠筛选更省总耗时时执行。沿用任务或回执简记理由。阶段检查点按本阶段验收条件核对证据，最终验收按最终版本核对全部强制项，并补足受影响回归和整体可用性证据。

“全量”应指项目约定运行器、范围和环境下的整套检查，不扩展成所有真实服务、平台和长期试验。沿用批准的运行器、隔离方式及环境条件，不能用裸自动发现绕过范围限制；针对性命令也须满足相同必要初始化与隔离。真实服务、本机能力、外部模型及其他高成本检查按相关变化和约定检查点执行，不因修复无关逻辑机械重跑。不同环境可能验证不同能力，先核对实际覆盖再判断是否重复。

## 证据、审阅与派发

复用证据须可定位被测版本、范围、结果和必要环境；核对相关实现及间接依赖、配置、数据、测试/夹具与运行器的变化。无关报告或文件变化不自动使全部结果失效；受影响结论补验，其余注明沿用依据。原失败、阻塞和未测继续保留，已有失败不能以“本轮没有新增失败”标成全套 PASS；无有效证据的项目不得算通过。

审阅者独立判断实际差异、测试是否测对了行为及证据是否足够。对约定必须独立实跑的检查、尚缺必要证据的行为或能改变结论的反例，补跑相关用例。按范围引用其余有效结果。一次实际操作或测试可同时作为多个验收项的证据。

在既有任务或修复意见里简述本轮必验行为、可沿用证据和完成条件。需要扩测时说明理由，历史命令和执行端自加的全量要求按本轮影响重新判断。日志先读摘要、失败或跳过项，诊断时展开相关片段。验收表引用本轮及已有证据，保留失败、阻塞和未测项。
