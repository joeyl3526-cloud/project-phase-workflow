# GPT 对 OpenCode 实现的严格审阅

每次审阅 OpenCode 的实现、修复及最终交付时读取，覆盖本轮差异及受影响的重要路径。GPT 承担技术审阅和方案判断；实现端报告提供线索，实际代码、原始要求和可复查证据决定结论。按 [测试策略](testing.md) 独立复做关键检查、复用其余有效证据，不机械复制实现端全套命令。

## 固定依据与对象

先恢复已批准 REQ/AC、design、接口契约、任务边界和前次问题；记录代码基线及本轮实际差异。高风险任务可在实现前准备少量需求驱动的关键反例；交付后仍须针对实际实现独立检查相邻组件和未覆盖组合，不把预设用例全过等同审阅通过。检查实际修改文件，包括未提交和新建文件，不能只相信回执的 changed_files。重要证据必须关联被测版本；审阅中发生行为相关变化后，对新版本复验受影响结论。

前端设计、组件、页面、样式、交互、前端状态和 API 接入代码均归 GPT/Codex。检查 OpenCode 是否越界或借助改测试、改验收、改共享契约隐藏问题；越界须记录并处理，GPT 确认所需改动及归属后再复验，不擅自覆盖用户并发修改。OpenCode 提出的接口调整先由 GPT 评估，不能自动成为批准的新要求。

## 从要求推导检查

1. 沿核心调用和数据路径阅读本轮实现及必要相邻代码，核对输入校验、业务规则、返回值和错误语义，查找看似完成但仍靠占位、假数据或静默降级的路径。
2. 根据真实场景主动找反例：空/边界/无效输入、重复操作、失败后重试、取消及恢复；涉及并发、持久化、外部服务、权限或不可信输入时，检查对应竞争、部分失败、一致性及隔离。只加入适用且有区分力的场景。
3. 检查模块职责、重复实现、不必要依赖、错误处理与资源释放、可修改性及关键性能风险；评估实际影响，性能收益未测时标为推测。
4. 独立复做关键验收和受影响回归，必要时补一个能暴露问题的用例。检查测试是否验证外部可观察行为、是否遗漏错误路径、是否为了通过而删减标准；测试数量、构建成功及执行端 PASS 不单独构成通过。
5. 将设计、后端行为与 GPT 负责的前端接入核对。接口字段、状态及错误处理有偏差时先修正对应实现或经确认更新契约，重新验证受影响的完整流程。真实与模拟、自审与独立检查分别说明。

## 主动寻找更好的实现

对本轮有实质影响的实现选择，主动考虑复用现有能力、更简单的结构/算法或不同的错误与状态处理。与当前方案比较正确性、实现复杂度、维护负担、适用的性能及变更风险，并记录推荐和依据；可合并为一张简表，已有有效比较直接引用。

只有确有价值的替代路径才进入比较，不为凑数量发明架构。改进能在批准范围明显减少缺陷、复杂度或维护成本时安排实现与复验；收益不明时做适量验证或记为可选建议。改变范围、公共接口或重要取舍时按原协作规则处理，不把个人风格当强制缺陷，不以“严格”为由无限重构。

## 问题闭环与放行

每项问题给出要求/契约依据、准确位置和版本、复现或代码证据、影响、修复或补证据的通过条件；标明严重程度，并区分必须修复、必要验证、一般问题及可选改进。怀疑尚未证实的标待验证，允许实现者提供反证。

强制项失败给 FAIL；缺少完成强制判断所必需的环境或证据给 BLOCKED，不能包装成 PASS。修复后复验原问题和相关回归，保留未测项；原有未关闭失败持续呈现，不能以无新增失败代替全套通过。依据本轮检查及仍有效证据，检查实际差异和相应范围强制 AC 均完成、无阻断缺陷且满足约定放行条件后，才能给注明范围的 PASS；可选优化不无期限阻止交付。

交回版本关联的审阅报告及验收表，明确实际可用范围、关键问题、替代路径判断和剩余缺口。OpenCode 执行成功、GPT 技术审阅通过和用户验收分别记录。只在审阅完成后记录桥接结论，A/B 与用户暂停规则保持原约定；后端任务通过不能代表整个含前端阶段已完成。
