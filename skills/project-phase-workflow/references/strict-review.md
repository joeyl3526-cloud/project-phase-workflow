# GPT 对 OpenCode 成果的审阅

审阅 OpenCode 的实现、修复和最终交付时，GPT 依据原要求、实际差异和可复查证据独立判断。按 [测试策略](testing.md) 复用有效结果，按约定执行独立实跑，补足影响审阅结论的证据缺口。

## 固定依据与对象

先恢复已批准 REQ/AC、design、接口契约、任务边界和前次问题。核对基线和实际修改，包括未提交及新增文件。沿受影响的调用链审阅，优先检查风险有证据且可能影响本轮结论的相邻组件和状态组合。重要证据须关联被测版本；审阅中发生行为相关变化后，复验受影响结论。

前端设计、组件、页面、样式、交互、前端状态和 API 接入代码均归 GPT/Codex。检查 OpenCode 是否越界或借助改测试、改验收、改共享契约隐藏问题；越界须记录并处理，GPT 确认所需改动及归属后再复验，不擅自覆盖用户并发修改。OpenCode 提出的接口调整先由 GPT 评估，不能自动成为批准的新要求。

## 从要求推导检查

1. 沿核心调用和数据路径阅读本轮实现及必要相邻代码，核对输入校验、业务规则、返回值和错误语义，查找看似完成但仍靠占位、假数据或静默降级的路径。
2. 从受支持的输入、真实使用场景和实际差异中选关键反例。补测以现有证据尚未覆盖、且可能暴露违反验收条件或既有支持承诺的行为为限。已有充分证据时结束检查。
3. 检查模块职责、重复实现、不必要依赖、错误处理与资源释放、可修改性及关键性能风险；评估实际影响，性能收益未测时标为推测。
4. 核对测试是否验证了可观察行为，重要错误路径是否有证据，以及验收标准有无被放宽。按测试策略决定需要补做的检查。测试数量、构建成功及执行端 PASS 各自只证明对应范围。
5. 本轮涉及前后端交互或共享契约时，核对相关字段、状态和错误处理。修正后验证受影响的用户路径。真实与模拟、自审与独立检查分别说明。

## 主动寻找更好的实现

对本轮有实质影响的实现选择，主动考虑复用现有能力、更简单的结构/算法或不同的错误与状态处理。与当前方案比较正确性、实现复杂度、维护负担、适用的性能及变更风险，并记录推荐和依据；可合并为一张简表，已有有效比较直接引用。

比较与本轮有实质关系的替代路径。现行实现满足验收且收益尚不明确的改进记为可选建议。改变范围、公共接口或重要取舍时按原协作规则处理。

## 问题闭环与放行

每项问题给出要求/契约依据、准确位置和版本、复现或代码证据、影响、修复或补证据的通过条件；标明严重程度，并区分必须修复、必要验证、一般问题及可选改进。怀疑尚未证实的标待验证，允许实现者提供反证。

强制项失败给 FAIL，缺少完成强制判断所必需的环境或证据给 BLOCKED。修复后复验原问题和实际受影响范围，保留未关闭的失败和未测项。本轮强制验收条件证据充足、无阻断缺陷且满足约定放行条件时，给注明范围的 PASS 并结束审阅，可选优化记入建议。

交回版本关联的审阅报告及验收表，明确实际可用范围、关键问题、替代路径判断和剩余缺口。OpenCode 执行成功、GPT 技术审阅通过和用户验收分别记录。只在审阅完成后记录桥接结论，A/B 与用户暂停规则保持原约定；后端任务通过不能代表整个含前端阶段已完成。
