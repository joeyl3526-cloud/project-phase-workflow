# 阶段 0 与 0.5 的文档完整性

在这两个阶段收尾、准备委派实现或发现设计缺口时读取。目标是让实现者能依据文件完成任务、让 GPT 能依据原要求审阅。按行为、接口和风险判断详细程度；不设页数、字数或固定文档数量，小项目可以合并文件。

## 阶段 0：需求基线

阶段 0 形成确认过的需求，详细技术设计在阶段 0.5 完成。requirements、acceptance 草案及 handoff 至少能回答：

| 内容 | 足够明确的判据 |
|---|---|
| 使用者与场景 | 谁在什么设备和情况下完成什么任务，当前困难及预期收益 |
| 核心流程与范围 | 入口、输入与输出示例，第一版必做、延后及不做的边界 |
| 业务规则与异常 | 影响产品行为的规则、关键边界和失败后用户怎么办；未知项显式列出 |
| 现实约束 | 适用的平台、联网与外部服务、数据与隐私、部署维护、性能兼容要求；不适用说明原因 |
| 可验证目标 | 稳定 REQ/AC 编号，代表性正常与失败场景，能观察的通过条件；真实/模拟/用户体验要求分清 |
| 决定与接续 | 已确认取舍及依据、待验证事项的处理安排、执行边界、本次实现模型与确认记录 |

GPT 逐项核对，补齐会改变目标、产品行为或授权范围的空白；需要用户决定的只问关键项。未验证前提保留不确定性，不写成事实。阶段 0 不以提前写完全部接口和页面细节作为结束条件。

## 阶段 0.5：可实施的设计与交接

GPT 负责整体方案、前后端接口及设计审查；前端设计采用 Design Dialogue 和 Frontend Design，前端实现与后续修改由 GPT/Codex 完成。每个第一版功能应有足够支撑实现及验收的信息；普通可逆细节保留自主空间。按相关性覆盖下表，不适用可注明理由；影响当前任务的关键未知不能用“按最佳实践”“后续完善”代替。

| 内容 | 足够明确的判据 |
|---|---|
| 需求对应与方案选择 | REQ 对应设计位置；少量实质路径的比较、选择理由和限制，已有有效比较可引用 |
| 完整流程与系统边界 | 用户操作、组件职责、输入输出及数据流；正常路径和主要失败/恢复路径可走读，复杂关系用图 |
| 页面与交互 | 页面/导航、关键操作、表单校验、空/加载/成功/失败及必要的权限状态；适用的响应式、键盘及可访问性行为 |
| 视觉依据 | 风格与主要设计变量、代表性可查看小样或原型、与实际版本对应的预览及检查结果；完整制作按小样和迭代约定推进 |
| 数据与业务约束 | 必要的数据实体、字段类型与必填/可空、标识关系、约束和状态转换；适用的持久化、迁移及恢复行为 |
| 跨边界接口 | 实际采用的 HTTP/IPC/函数/事件等接口：名称、输入输出结构与示例、校验、错误及权限语义；按需明确超时/重试/取消、幂等、分页、排序、时间及单位 |
| 技术与运行条件 | 组件及依赖、既有代码复用、目录边界、配置名称、启动构建及部署办法；配置只写名称和位置，关键可行性给实际证据及限制 |
| 任务与归属 | 每项任务的负责人 GPT/OpenCode、允许修改与禁止修改的路径、依赖、REQ/AC、完成条件和审阅检查点；共享类型/配置明确单一负责人 |
| 验收与回归 | AC 的前提、具体输入、操作、预期与通过标准、检查方法与环境；核心流程、主要异常、前后端接口一致性及受影响回归有安排；按 [测试策略](testing.md) 区分本轮相关检查、综合检查点及高成本检查条件 |
| 未决事项与版本 | 已确认、假设、未验证、不做分开；未决项的影响、处理人和检查点明确；现行文档版本及用户确认依据可定位 |

前后端共用接口和类型由 GPT 定义并审查。OpenCode 可提出调整建议；改变已确认行为、公共接口或前端依赖前，由 GPT 同步评估及更新设计，涉及重要取舍按已有授权处理。不得让 OpenCode 为了联调或测试通过顺手修改前端。

维护简短对应表，可放在 design、acceptance 或任务表中：

| REQ | 设计/接口位置 | 实施任务及负责人 | AC | 实现后证据 |
|---|---|---|---|---|
| 项目实际编号 | 可定位章节或文件 | 任务标识、GPT/OpenCode | 实际编号 | 实施前标待执行，实施后关联版本补入 |

不得用文件名列表代替对应关系，不编造尚不存在的成果、行号、测试结果或确认。

## 收尾与派发前核对

GPT 完成一次文档走读并记录结论：

1. 从实际 REQ 出发，把核心正常流程和主要失败/恢复流程走到预期输出；核对页面所需字段、接口定义、数据规则及 AC 是否一致。
2. 以交接文件为唯一业务依据尝试说明下一项任务的输入、输出、边界、修改范围和完成判断。实现者仍须猜测的重要行为转为明确规则、试验或待决问题。
3. 将检查结果及剩余缺口写入现行 handoff；影响核心流程、跨端契约或强制验收的缺口先解决，再委派受影响任务。允许不依赖缺口的已批准任务继续。
4. 正式派发携带相关 requirements、design、acceptance、handoff、接口/类型及必要样本的可读取路径和版本，明确负责人和路径边界；只传一段聊天摘要不足以代替它们。使用桥接时纳入 required_files 和 context，保护本轮批准依据，检查上下文指纹。

阶段 0.5 收尾向用户说明方案、关键取舍、文档检查结论及剩余限制，沿用既有确认与 A/B 规则。后续实现出现新事实时，GPT 在对应检查点重审设计及相关证据，更新现行文件并同步给下一次派发；前期文档不能替代持续审阅。
