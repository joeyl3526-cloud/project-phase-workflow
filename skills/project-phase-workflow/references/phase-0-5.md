# 阶段 0.5：方案、交互与可行性

承接已确认目标与阶段 0 选定的后续实现模型，读交接、需求、验收草案及相关代码和环境；已有有效模型确认直接沿用。只补影响本阶段的缺口，必要时验证模型可用性与执行端兼容。

前端方案由 GPT/Codex 使用 Design Dialogue 与 Frontend Design 完成；需求明确时直接承接，不额外强制访谈。明确页面、状态、视觉依据及前后端接口，先检查代表性小样。前端正式实现及修订由 GPT 负责，OpenCode 只接获准的非前端任务。详尽程度按 [文档完整性](handoff-quality.md) 检查，允许小项目合并文件。

## 先处理关键疑问

找出最可能造成失败或大量返工的问题，如真实输入处理、外部连接、设备能力或操作理解。按需要做最小试验或原型：先定问题、代表性样本和判定条件，再执行并记录结果、限制和证据。原型可以只回答一个问题，标清演示与真实能力。

视觉任务先约定代表性小样及通过标准，检查关键帧、低清预览或短片段等小样，通过后再进入完整渲染等高成本制作。

先验证哪部分由风险和依赖决定，允许从交互、核心算法或外部连接切入。关键前提无法成立时，说明影响，给出可行调整；可独立的设计继续推进。

## 形成足够实施的方案

沿完整任务说明入口、输入、处理反馈、输出、保存和失败后的操作。按场景覆盖首次使用、空数据、处理中、成功、失败及重启恢复；简单项目用文字和示例，交互难判断时用线框或可操作原型。将目标用户依指引独立启动并完成核心任务列为验收行为。

承接全局计划探索规则，用表格比较少量有实质差异的路径，再推荐适合当前规模的方案；已有有效比较直接引用，只有一条合理路径时说明原因。交代必要组件、数据流与存储、接口、依赖、启动配置、成本及适用的备份恢复，评估后续修改与维护负担，记录关键选择理由。区分已选方案、可替换细节和待验证假设，给实现者保留合理空间；新证据影响重要取舍时说明调整及影响，按共同规则取得对应决定。

## 准备实施

细化 AC：目的、对应需求、是否强制、前提与数据、步骤、预期、通过标准、检查方式、真实环境及用户体验确认要求。性能和兼容指标依据实际需要确定。测试计划与执行结果分别保存。

按可观察成果拆任务，注明 GPT/OpenCode 负责人、允许/禁止修改的路径、共享文件归属、优先级、依赖、REQ/AC、完成条件、阶段审阅检查点及交回内容，尽早贯通核心流程。涉及多个相互影响状态或组件的高风险工作，优先拆成可独立验证且保留业务意义的小批次，不机械按文件拆分，不额外增加用户审批。更新 design、acceptance、handoff，按共同记录规则保留实际采用的资料来源；重要试验证据进入 reports。

对持久化、并发、权限或外部副作用等确有风险的功能，按需求在实现前选少量关键状态组合和反例，写清前提、操作顺序与预期；可先准备验收场景或可执行用例，低影响改动无需增加此步骤。提前准备不替代交付后对实际成果的审阅和探索。

GPT 按文档完整性参考核对数据及接口契约、状态与异常、任务归属和 REQ→设计→任务→AC 的对应关系，走读核心正常与失败流程，在 handoff 记录结论和未决项；关键缺口解决后再派发受影响任务。向用户呈现方案与交互摘要及检查结论，确认重要取舍和执行边界；准备正式实施时按技能入口核对执行端与 A/B。

出口：需求与方案一致，核心交互及接口明确，文档走读通过，致命不确定性已处理，任务归属与验收可执行，重要选择已确认。
