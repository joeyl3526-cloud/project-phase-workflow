# 阶段 2～n：增量实现与审阅

从项目交接恢复当前阶段、已批准目标、执行端、A/B、成果基线及相关 REQ/AC。保留仍有效的决定；阶段编号由本项目计划确定。只有范围尚不明确时补少量必要信息。

每阶段以可观察成果划分：批准的增量目标 → 实现 → 自检 → 审阅 → 修复或补证据 → 按 A/B 接续。开始前明确本轮成果、受影响的已有能力和通过条件，避免按文件数或技术层机械分期。高成本任务按约定的草稿轮数、检查点等迭代边界执行；达到边界时交回已有成果、问题和建议。

涉及多个相互影响状态或组件的高风险增量，先从需求选少量关键组合场景或反例，明确通过条件，再按可验证的业务成果拆小批次；普通低影响改动无需增加此步骤。提前准备不替代交付后审阅，也不增加用户审批或改变 A/B 推进。

GPT 负责本轮前端实现与修改；OpenCode 只做批准的非前端任务，沿用已确认的接口、路径及共享文件归属。实现者读取本轮必读依据，核对已有改动和依赖，完成足以交回的增量。按 [测试策略](testing.md) 选择新增行为与相关回归、复用有效基线，并在需要时扩大检查；不因小改、修复轮或阶段编号默认全量。持久化涉及重开读取，界面涉及实际操作，外部服务分别标明模拟和真实范围。普通方案细节可自主调整；新增需求和关键计划调整按全局规则分析，重要目标变化回到受影响的需求或方案讨论。

交回可定位的版本和差异、相关 REQ/AC、检查输入及环境、结果与证据、已知限制。验收清单注明本轮执行与沿用证据。GPT 按 [OpenCode 成果审阅](strict-review.md) 核对原要求、实际差异和证据，按测试策略执行约定的独立检查并补足证据缺口。审阅期间固定对象，行为相关变化后复验受影响结论。

问题说明要求、证据、影响和通过条件，区分强制缺陷、必要验证与可选建议。实现者可提出反证，按要求和证据解决。重复失败且没有新证据时先改进诊断；不降低强制标准或无限优化。

A 在批准范围内继续普通修复、复验和下一阶段；B 在本阶段执行、自检与审阅后交回结论和推荐，等待用户批准下一范围，即使通过也等待。批准单项修复不等于切换 A，修复不改阶段编号。明确暂停后保存状态，不让迟到完成事件重新启动任务。

通过仅覆盖注明版本、环境及检查范围。更新 handoff 和必要使用说明；还有批准任务时按模式接续，全部批准阶段完成后转最终验收。新想法进入待办。
