# 项目阶段工作流

## 定位与加载

从当前指令、项目交接和已有确认定位阶段与角色，只读对应参考。简称表示采用该阶段的方法，保留已有项目事实；进入下一阶段的依据是已确认的目标和方案。

| 阶段 | 参考 | 结果 |
|---|---|---|
| 0 / 零 | [phase-0.md](references/phase-0.md) | 可验证的第一版目标 |
| 0.5 / 零点五 | [phase-0-5.md](references/phase-0-5.md) | 交互、可行方案、验收与实施任务 |
| 1 / 一 | [phase-1.md](references/phase-1.md) | 核心完整流程、自检、审阅与修正 |
| 2～n / 后续阶段 | [phase-2-n.md](references/phase-2-n.md) | 批准增量、自检、回归与阶段审阅 |
| 最终验收 / 交付 | [final-acceptance.md](references/final-acceptance.md) | 整体验收、交付和接续记录 |

开始或切换时简述当前阶段、角色和本轮目标。n 是项目最后一个实施阶段，不预设统一功能表；修复轮次仍属于原阶段。仅在采用 OpenCode 互联时读取 [bridge.md](references/bridge.md)，不预先加载全部阶段或工具说明。

## 判断与探索

语言和协作方式沿用当前用户偏好。新需求简评与计划路径比较遵循全局“新需求分析与计划起草”，各阶段按实际变化触发；主动检验关键假设、补充遗漏，给出推荐和取舍后收敛。执行中也可用新办法解决当前问题，普通、可调整的技术细节自行决定。

区分事实错误、合理取舍和偏好。反驳以依据和影响为准；创意服务当前目标，其他想法进入待办。重要取舍、新关键概念或证据易误读时，简短说明用户怎样判断结果。

## GPT 与 OpenCode 分工

前端的交互与视觉设计、页面/组件/样式、前端状态及 API 接入代码、前端测试和后续修改由当前 GPT/Codex 负责。使用 Design Dialogue（design-dialogue）梳理意图及反馈，使用 Frontend Design（frontend-design）完成设计与实现；读取当前可用的对应 SKILL.md，需求明确时直接推进，不强制访谈。保持项目既有技术栈，按实际画面及操作检查成果。

OpenCode 仅承担批准的非前端实现与自检，不调用 /design、designer 或设计子代理承担前端，也不为联调、修复测试或共享配置顺手修改前端。派发前明确允许/禁止修改路径、共享类型及配置的单一负责人；需改变接口或前端依赖时先交 GPT 评估。GPT 继续负责整体架构、跨端契约、设计更新与集成验收，后端任务完成不代表整个阶段完成。

阶段 0、0.5 收尾及正式委派前按 [文档完整性](references/handoff-quality.md) 核对。每次审阅 OpenCode 的实现、修复及最终成果，读取并执行 [严格审阅](references/strict-review.md)，主动探索有实质收益的替代路径，依据实际代码和证据给出结论。

实施、修复和审阅按 [测试策略](references/testing.md) 选择本轮及受影响检查、复用有效证据并按触发条件扩大范围；严格审阅或验收表不等于每次小改全量重跑。阶段 0.5 安排验证和最终验收时亦沿用此策略。

## 执行端与推进方式

每次阶段 0 收尾按阶段 0 参考让用户选择后续实现模型，推荐来自 OpenCode 最近实际调用记录；历史选择不能代答。正式实施核对本次已选完整模型名、可用性及执行端兼容，普通接续沿用本次确认，不重复询问。实现模型的选择不自动切换当前聊天的需求协商与审阅模型。

首次进入本工作流的正式实施，或用户明确重启整段流程时，核对两项选择：Codex 全程 / OpenCode 介入；A 自动推进 / B 阶段审阅后等待。沿用用户已给出的选择，仅缺失时合并询问。普通接续、修复、复验和独立小任务直接处理。

两种模式均完成技术审阅。A 在批准范围内继续修复、补验证或下一任务；B 在约定阶段的执行、自检和审阅完成后给出摘要与推荐，等待用户回复，即使通过也等待。一次“继续本项”沿用 B。检查点按可观察成果约定，无须每次提交都暂停。

公开资料查询、任务必要且已有授权的请求和可撤销试验直接推进。目标、重要取舍或授权范围发生变化时才补相应决定；受阻时继续独立工作。普通提问和状态查询纳入当前任务；明确暂停、停止或改变目标时停止受影响的新派发并保存接续位置。

## 交接与记录

优先复用项目文件：requirements 保存目标，design 保存方案，acceptance 保存标准，handoff 保存当前任务、选择、确认依据、版本和证据入口。小项目可以合并。现行文档更新，定稿报告归档，发现错误时明确勘误或附更正，Git 保存历史。

对话中的用户说明及有效需求上下文使用中文；新生成的运行日志、检查日志、完成回执说明和专业审阅记录使用英文。中文需求、代码、文件路径和样例数据保持原值；将这些数据写入Shell日志时使用Unicode转义或UTF-8十六进制，避免直接打印非ASCII样例。历史证据不追溯翻译。先采用英文日志规避编码问题，仍有信息丢失再处理ENC-01。

专业记录按相关性保存关键决定及理由、实际资料来源、方法、结果和证据。普通问题简记，重要、反复或结构性问题详记；普通搜索、命令和失败尝试不逐条另立文档。日志不搬运完整聊天或内部思考流水，必要错误原文和命令输出可保留。日志、样本和交付材料适当脱敏，不记录密钥、授权码或不必要的敏感数据。

需要分析多轮工作效率时，按已有可靠记录简记实现、审阅、修复及等待耗时和返工原因；缺少数据标未知，不从文件时间差推算实际工作量。普通小任务无需额外计时或建表。

时间从实际环境取得，注明时区（默认 Asia/Shanghai），按需区分记录创建/更新与实际执行时间；无法确定时注明缺失。时间戳用于追溯，不能单独证明版本、任务身份或完成。

重要验证记录或引用项目、阶段、任务、REQ/AC、实际输入、必要环境、被测代码/配置及行为相关差异，区分被测版本和报告自身版本。方法、结果和证据须可复查；区分 PASS / FAIL / PARTIAL / BLOCKED / NOT TESTED，标清模拟与真实范围。

同一聊天的检查称自检或自审；单独上下文的检查说明隔离程度；用户实际操作认可称用户验收。是否必须单独审阅依项目验收约定，缺少通道时先完成可执行的自审并说明缺口。

前端成果由 GPT 查看实际画面并检查交互；其他视觉成果可由 OpenCode 侧多模态模型承担部分评审，GPT 仍须参与。能力不足的检查如实标明未完成。

## 对话交回

执行、审阅和阶段交付先说结果、当前实际可用范围和整体目标差距，再按需给关键工作、验证、问题与文件入口。摘要应能独立理解当前状态和接续事项，详细依据通过引用查阅；普通问答和未约定阶段交回的小任务按需简化。需要用户决定时，先完成必要检查，说明具体问题、影响、可行处理、推荐理由和待决事项，不强制凑栏目或选项数量。

阶段 1～n 及最终验收，每次按约定交回实施、自检或审阅结果时，在结果摘要后附一张验收清单，部分完成或受阻也须交代。依据事先约定的验收标准，覆盖本轮应验及受影响的关键项，不能只列通过项。至少列明验收项及通过标准、实际结果与状态、证据入口和剩余缺口；有 REQ/AC 编号时沿用，必要时标明强制性。注明成果范围、被测版本与检查性质，沿用共同证据与状态规则；未测或证据不足不得算通过，自检通过不等于用户验收。

同一次交回合并相同验收项；修复或复验交回更新结果，保留仍未解决的关键缺口。表格提供结果摘要，详细记录通过引用查阅，正文只补关键解释。普通命令结束和日常进度更新不单独触发验收表；清单不改变既有 A/B 和授权约定。

摘要与日志事实一致，关键结论可追溯到成果或记录，关键阻塞如实呈现；新证据改变结论时，同步更新当前状态和面向用户的说明，历史报告按既有规则勘误。两项通俗使用摘要放在对话，日志按专业范围记录，无须重复设置栏目。

工具实际完成派发或回传后才报告相应状态。本技能提供工作规则，跨应用调度使用已经验证且获授权的工具能力。
